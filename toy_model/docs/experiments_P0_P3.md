## 2. P1：固定角色事实覆盖，只改变伙伴数（§4）—— ✅ 完成（结果见 §7）

### 2.1 数据构造

> 对每个H关系j：
> 1. 固定100个bridge为U_j（20%），剩余400个为S_j（80%）。所有臂使用完全相同集合。
> 2. 12个T伙伴中，固定4个仅用于该H的新pair测试；其余8个按预先随机顺序形成嵌套集合，k=1/2/4/8取前k个。伙伴划分可按H随机、但在臂与seed之间共享。
> 3. 每个b∈S_j，在每个训练伙伴T下构造 `h=T^{-1}(b)`，答案为H(b)。
> 4. 每个b总共获得8次第二跳监督：k个伙伴各重复8/k次。
> 5. 每个H在四臂中都具有400个已覆盖角色事实、3,200次目标答案监督；8个H共25,600次监督。每个事实的总权重相同。
> 6. 对所有伙伴、所有训练行，禁止在第二跳调用H(U_j)。H在U_j上的原子题仍完整训练。
> 7. 全部H→H训练为0。
>
> 训练内容中unique三元组数为每H的400k，会随k改变；重复次数相应下降。**这就是本实验操纵的新伙伴上下文数量**，不能宣称unique训练样本数也相同。

- ✅ 1–7 全部按原文实现于 `src/data/builder_role_control.py`（`--role_unseen 100 --role_reserved 4 --role_exposure 8 --role_seed 7`）。U/S 集、伙伴顺序、保留伙伴由独立的 `role_seed=7` 生成，在所有臂和训练 seed 间相同（写入 `meta.json: role_split`）。重复曝光实现为训练行的字面重复（8/k 份），不去重。
- ✅ 审计（`scripts/audit_role_control.py`，从 `train.json` 实际行重算）在 k=4 数据上通过：每个 H 第二跳覆盖恰 400/500、U 违规 0、每个已覆盖事实曝光 8/8、保留伙伴违规 0、H→H 训练行 0、U_j 上的原子题每个出现 8 次；所有组合测试类型与训练行零重叠；k=4 的 unique 组合 52,800（40,000 基础 + 8×400×4），总监督答案 145,600/epoch。四个 k 的 `audit.json` 由作业里的数据目录生成后同样可查。

### 2.3 初始化与训练预算

> - 用对应训练seed的 `F_long_s{1,7,123}/epoch3000.pt` 初始化；同seed四臂使用同一份权重。先核验checkpoint的原始训练数据无H组合。
> - 当前checkpoint不保证包含optimizer状态；主实验统一重建AdamW，不把它称为无缝延长原训练。模型权重、优化器重置及调度规则写入manifest。
> - 保持2L/d256/2head、RoPE与原实现一致，AdamW lr=3e-4、wd=0.1、warmup=100 optimizer updates，之后常数lr。
> - 主终点：**200,000次新增optimizer updates**。不按epoch停止，也不根据目标测试集决定延长。
> - 每次更新256个单答案逻辑任务：128个共同T→T重放、64个共同单原子任务、64个P1角色训练任务。
> - 原子流对全部关系/实体均衡；T→T流使用相同冻结manifest；角色流先按同一(j,b)调度，再按不同k分配伙伴。每类流的ID、次数与loss权重均可审计。
> - 对本批256个监督答案统一取均值；若分microbatch，按监督答案数累积后统一归一化，再调用一次optimizer.step。
> - 所有臂每步的类别数量和每(j,b)曝光计划相同。每8次同一(j,b)曝光完成一个伙伴平衡周期；允许把它实现为固定宏批次而非强求256内整除所有关系。
> - 500-update smoke仅检查数据、运行与保存；不按held-out表现选参数。主运行采用独立新目录，不复用smoke输出。

- ✅ 初始化：`train.py --init_from ../runs/skills_F_long_s{seed}/epoch3000.pt`（PBS 驱动把 `{seed}` 换成运行 seed），只载入模型权重，AdamW / warmup 从零重建，`train.log` 里打印 "optimizer state is fresh"。F_long 的数据（`data/skills_F_long/meta.json`，P0 的 `role_coverage.json`）核验为零 H 组合。
- ✅ 2L / d256 / 2 head / RoPE 不变；lr 3e-4、wd 0.1、warmup 100、之后常数（`configs/skills_w2d2.yaml` + cell 覆盖）。
- 🟡 主终点 200k updates：`train.py` 只按 epoch 停止，所以每臂的 epoch 数按 "200,000 / 每 epoch 更新数" 取整设置：单角色臂 97,661 行 → 382 更新/epoch → **525 epoch = 200,550 updates**；RC_none 72,061 行 → 282/epoch → **710 epoch = 200,220**；RC_both4 123,261 行 → 482/epoch → **415 epoch = 199,930**。偏差 < 0.3%。没有按目标测试集延长。
- ❌ **固定的每步逻辑流（128 T→T 重放 + 64 原子 + 64 角色）没有实现。** 实际做法：把 F_long 的全部训练行（单任务行 8,048、宽 1–4 行 24,013、T→T 组合 40,000）与角色行（每 H 3,200）合并成一个数据集，每个 epoch 整体打乱、batch 256 行，loss 是该 batch 内所有监督答案位置的均值。理由：现有训练循环是"按行"的，宽度行带 1–4 个答案，要做到每步固定类别数需要新的采样器和按答案数的归一化；在本轮时间内没有实现。后果与可审计之处：(a) 每 batch 中角色行的期望比例 = 25,600/97,661 = 26.2%（提案 25%），T→T 组合 41%，原子行 33%（答案数更多）；(b) 每个已覆盖事实每 epoch 恰好 8 次曝光（审计），"伙伴平衡周期"是一个 epoch 而不是 8 次更新；(c) 四个 k 臂的行数、答案数、每 epoch 更新数完全相同，因此每步类别数量在期望意义上相同，不是逐步严格相同；(d) RC_none 与 RC_both4 的行数不同，用 epoch 数补偿更新数（见上）。
- 🟡 smoke：做了本地数据生成 + 审计（`/tmp/.../rc_second_k4`），没做 GPU 500-update smoke；主运行使用全新目录 `runs/skills_RC_*`。

### 2.4 固定评估集

读法（3 个 seed-1 checkpoint + 1 条时间线 + RC_k1/k4 seed 1；其余 seed 待补）：

1. **bridge 在第一层、r1 位置以与上下文无关的形式算出，第二跳经注意力从该位置读取。** 换成另一个 (h', r1') 但同 bridge 的源状态，T→T 与 T→H 的准确率都不降（0.98–0.99；0.717 vs 0.672；0.864 vs 0.908）；错误 bridge 的 T→T 题 0.98–1.00 跟随源；位置 2 的第一层状态交换无效。时间线上，"跟随源 bridge" 与 T→T 组合准确率同步出现（epoch 400–800），不早不晚，尖峰 checkpoint（600）两者同时塌掉。
2. **"跟随"的比例由源 bridge 的 role2 覆盖决定，而不是由目标题决定。** F_perrel1：已覆盖源 0.66–0.70、未覆盖源 0.30–0.38，与行为读数（0.67 / 0.22）一致；F_pairleak8 新伙伴：0.86 / 0.57 vs 行为 0.91 / 0.18。给定一个正确的 bridge 状态，"能否输出 H(b)" 在未覆盖事实上明显更低。
3. **未覆盖角色事实的失败不是第一阶段（bridge 计算）的问题**：正确 bridge 状态注入不能恢复未覆盖题（same_bridge 0.28 / 0.16 / 0.54，与 no_patch 持平）。对应提案第 5 条的第二种情况：源状态可被第二阶段读取（T→T 与已覆盖源都跟随），但第二跳知识 H(b) 对未覆盖 b 不可访问。
4. **零覆盖对照**：F_long 上 H 的原子题 100%，但把任何 bridge 状态送给第二跳的 H，输出既不是 H(b) 也不是 H(b')（0.010 / 0.004）——"原子形式可用，角色形式不可用"的最干净版本。
5. **训练伙伴上下文提高对未覆盖 bridge 的读出**（F_pairleak8：leakpair 0.536 vs 新伙伴 0.167，同为未覆盖源；行为 0.584 vs 0.181）。位置 1 已被替换，所以这个差别来自目标位置 2 的状态（它仍看到原来的 (r1, r2) pair）：pair 是否训练过会调制第二跳的应用。P1 的测试全在保留伙伴上，衡量的是"更多伙伴上下文能否让新伙伴上的应用更稳"，与这里的 pair 效应不同。
6. **（2026-09-16 撤回并更正）** 原文此处写"random_src ≈ 0 说明单任务行里 r 位置的状态不能被第二阶段读取"。这是错的：`random_src` 取的是 `<e_x><r_T><e_ans>` 在位置 1 的 block-0 状态，因果模型下它与 `<e_x><r_T><r2>` 的位置 1 状态完全相同（N0 脚本核验最大绝对差 0），所以它只是一个"均匀随机 bridge"源；脚本当时没记录源 bridge，所以只报了原答案准确率。从已保存的逐例预测重算跟随率（预测 == r2(T(x))）：F_long T→T 897/900，RC_k4 T→T 900/900、rc2 见过 822/900、rc2 没见过 834/900，RC_first4 rc1 没见过 898/900；RC_k4 按源 bridge 覆盖分层：已覆盖 717/719，未覆盖 105/181。即随机原子源的 bridge 被正常读取并应用。`scripts/patch_bridge.py` 已改为记录源 bridge 并报告跟随率。见 `findings_and_next_experiments.md` §2.1 与 `audits/2026-09-16/p3_audit.md`。
8. **零 H→H 监督下的 H→H 连接走的是同一条 bridge 通路**：both 臂的 H→H 题在 r_H1 位置算出 bridge、由 H2 读取；其损耗主要来自 H1 作为第一跳的 bridge 计算不如 T 稳定（注入 T 算出的 bridge 后 0.64 → 0.94），第二阶段与 T→T 相同。
7. **两个角色的失败发生在不同阶段。** 第一跳（RC_first4）：未覆盖输入的失败是 bridge 计算失败，注入正确 bridge 后 100% 恢复；第二跳（RC_k1/k4）：未覆盖 bridge 的失败是 H 应用失败，注入正确 bridge 不恢复。行为上第一跳对未覆盖输入几乎不迁移（0.02–0.07），第二跳随伙伴数迁移到 0.75（P1）。

读法：在**角色事实覆盖（400/500）、每事实曝光（8 次）、总监督量和更新步数全部固定**的条件下，伙伴数 1 → 2 → 4 → 8 让未覆盖角色事实的新伙伴成功率从 0.02–0.15 升到 0.38–0.47、0.63–0.70、0.75–0.77（单调、趋于饱和），已覆盖事实从 0.20–0.55 升到 0.96–0.99、≥ 0.995、≥ 0.999。这支持 H2（跨上下文共享的调用方式，随伙伴多样性变强），否定"k 的作用只是覆盖率"（H1）在本 regime 下的解释。训练伙伴上的未覆盖 bridge（`rc2_trainpartner_unseen`）与新伙伴上的几乎相同（k4：0.65 / 0.69 / 0.63），说明对未覆盖事实的迁移不依赖伙伴是否训练过。§1.3 的 P0 里 k=1 从零训练（F_perrel1，2000 epoch）的已覆盖事实读数（0.67–0.80）高于这里续训 525 epoch 的 k1（0.20–0.55）：k=1 时 8 次字面重复的行很快被记住（训练 CE ≈ 0.001），泛化上升缓慢。

读法：**训练里 H→H 严格为 0**（生成器与审计双重断言）时，只要 H 在两个角色上分别被接入（新伙伴 H→T 0.88–0.96、T→H 0.97–0.99），两个角色事实都已覆盖的 H→H 就达到 0.79–0.90（3 seed，8 个 H 一致，配对区间远离 0）。提案 §5.3 的反证条件（H→T、T→H 都 ≥ 95% 而 H→H 低 ≥ 10pp）没有被触发：H→T 不到 95%（0.88–0.96），H→H 比 H→T × T→H 的乘积低 4–7pp，属于"两个角色分别可用即可连接、损耗约等于两跳各自失败率之和"的量级。乘积列是事后计算，不是预注册模型。任一角色事实未覆盖时 H→H ≈ 0，与两个单角色臂的未覆盖读数（第一跳 0.02–0.07）一致。

**意外的交互**：both4 臂里第二跳未覆盖 bridge 的迁移只有 0.018 / 0.085 / 0.093，而只训练第二跳的 RC_k4 是 0.646 / 0.697 / 0.632（同 k=4、同覆盖、同每事实曝光；both4 每步角色行占比 41% 而非 26%，总 H 组合曝光多一倍，更新数同为 ≈ 20 万）。加入第一跳角色行后，第二跳对未覆盖事实的迁移消失，已覆盖事实不受影响（0.97–0.99）。这正是提案 §5.2 预留的"单角色双剂量"对照要分辨的：是第一跳行本身，还是角色行总剂量/混合比例造成的。未提交，列为下一步。
