## 2. 臂与 run

| run | 臂 | 说明 |
|---|---|---|
| D1–D3 | **D（主）** | 程序设 R = d，seed 1 / 7 / 123 |
| H1–H3 | **H（主）** | 学习 CONTINUE / STOP，λ = 0，seed 1 / 7 / 123 |
| P1–P3 | P（附加，不属于主对照） | 论文式随机预算 `R ~ clip(Poisson(4), 2, 8)` 每 batch 一个，最后一轮答案 CE；测试用所有深度共用的固定 R 网格，主读数 R = 8 |
| C1–C3 | Hc（附加，不属于主对照） | H + 弱计算成本 λ = 0.01（方案列为后续消融；λ = 0 时"永不主动停止、全部质量落在尾部"是无代价的解，这一臂并行给出对照） |

附加臂是方案里明确列为"后续候选"的两项，用户要求"一起提交"且 gj26 资源充足，所以并行跑；它们单独报告，不进入 D / H 主比较。显式 STOP 标签、固定阈值停止的训练版本仍未做。

## 3. 评估

- 每 10k updates（另加 1k / 2k / 5k）：全 10k 原子、1,000 道未见关系对 d2 验证、1,000 道 d2 训练行拟合、监测集（每格前 100 题 × 24 格），都用该臂自己的协议；H 另记同权重强制 R = d 的监测读数。
- 最终（1M）：全 120,000 题按主协议；同一权重的诊断——强制 R = d（全量）、所有深度共用的固定预算网格 R ∈ {1, 2, 4, …, 256}（每格前 500 题）、论文 §6.3 的 KL < 0.01 且熵 < 3.0 停止规则（每格前 500 题）、H 的采样停止；原子与 val_d2 的固定预算读数。
- H 的主指标 = **主动 STOP 且答对**；另报 timeout、错误停止、平均与分位循环数。D 的 R = d 不算学会停止。

## 4. 接入前检查（`python scripts/test_loop_gpt.py`，CPU，全部通过）

1. 每轮复用同一组 4 个 block；LM head 就是 embedding 矩阵本身（同一 storage，两处使用都回传梯度）。
2. 因果 NoPE：同一 `[x, r1]` 后接不同 r2，5 轮后 x、r1 位置的 hidden state 完全相同，末位不同。
3. 右 padding 不改变最后有效位置的读出；129 token 的 d = 128 输入完整处理，改最后一个关系输出即变；模型接口只接收 token。
4. w2 拆出的两个原子查询批量前向 = 各自单独前向。
5. 初始时 `F_θ` 为恒等（残差输出投影为零）但每个 block 都有梯度；stop head 只在 H 有梯度。
6. D 的 loss = 原子行第 1 轮、d2 行第 2 轮的手工计算；H 的终止分布在展开轮上和为 1（剩余质量在末轮），λ 项 = λ · E[T]。
7. H 的逐样本停止推理（active set 逐轮收缩）与逐题参考实现的停止轮、该轮答案、timeout 完全一致。
8. 三个臂同 seed 的骨干初始化 hash 相同；D / P 的 stop head 不进入 AdamW state；三个臂 8 updates 直跑 = 4 + resume 4（权重、AdamW 动量、来源流、R 流、计数器）。
9. 完整 run 写出 `final_eval.json`（主协议、强制 R = d、固定网格、KL / 熵规则、H 的采样停止）。

## 5. 作业与速度

**正式作业（一节点一任务；`-v RUN=<id>,PREC=tf32,GRAPH=1`）：**

| 作业 | run | 项目 | walltime | 状态 |
|---|---|---|---|---|
| 3396750–3396752 | halt-D1 / D2 / D3 | go39 | 4 h | 排队 09-19 17:00 |
| 3396753–3396755 | halt-P1 / P2 / P3 | go39 | 9 h | 排队 |
| 3396756–3396758 | halt-H1 / H2 / H3 | go39 | 16 h | 排队 |
| 3396759–3396761 | halt-C1 / C2 / C3（Hc） | go39 | 16 h | 排队 |
| 3396346–3396357 | 同样 12 个 run 的第一次提交（gj26，fp32 普通模式，walltime 12–36 h） | gj26 | — | 开跑前撤回：gj26 项目的同时运行作业数是 23 / 24（其他用户），调度器预计次日才开始；长 walltime 也不利于回填 |

为什么回到 go39：gj26 的瓶颈不是 token 而是**项目同时运行作业数上限 24**（提交时 23 个在跑）；go39 当时 0 个在跑、余额约 169 node-hours，12 个紧 walltime 作业合计预扣 135。walltime 不够就用同一条命令续跑（`--resume` 精确）；go39 拒绝时驱动脚本支持 `-W group_list=gj26`，也支持一个多节点作业里每节点一个 run（`RUNS=H1+H2+…`，pbsdsh 已验证可用），用来绕开作业数上限。

**速度实测（GH200，每 update）：**

| 配置 | D | H（展开 8 轮） |
|---|---|---|
| fp32 普通 | 18.9 ms | 135.8 ms |
| fp32 + CUDA graph | 11.2 ms | 118.3 ms |
| TF32 + CUDA graph | 8.3 ms | 102.7 ms |
| bf16 autocast + CUDA graph | 8.1 ms | 102.0 ms |

- 验证作业 3396345：D 的普通模式与图模式 300 updates 后**权重差为 0**，logged loss 完全相同；H 的图捕获第一次失败（`cumprod` 的反传会与主机同步），已把存活概率改为 log 空间的 `exp(cumsum(logsigmoid(-s)))`，数学等价、数值更稳。
- benchmark 3396457 / 3397213：上表；TF32 与 fp32 的 loss 逐点相同到 4 位小数；P 的 7 张图（R = 2…8）捕获正常，P 为 26.7 ms（普通）/ 12.6 ms（图）。**上表的数字包含了第 200 步（= 该测试的最后一步）触发的一次完整监测评估**，H 的评估要跑到 256 轮上限，所以 H 的 103 ms 大部分是评估摊销，不是训练步本身：CPU 上实测 H（展开 8 轮）的前向 + 反传与 P 在 R = 8 时相同（1.07 s 对 1.14 s），按 D / P 的斜率推算 H 的训练步约 20 ms。我一度把 H 的慢归因于读出的高级索引反传并改成了 `gather`（前向数值不变，保留），这个归因是错的，以正式 run 的 `train_log.jsonl` 为准。
- 估计 1M updates：D ≈ 1.5–2.5 h，P ≈ 3.5 h，H / Hc ≈ 6–8 h（含约 100 次监测评估）；实际值待正式 run 的日志。
